# 文档写作规范（Document Style）

本文件规定本仓库每一份文档的写作与排版规则。新增、改写或翻译文档之前，先读这一份。英文版见
`docs/doc-style-en.md`。**英文版 `docs/doc-style-en.md` 是规范版本。** 两者在措辞上冲突时，以英文版为准，中文版在同一次改动中改正。事实问题以 §4.3 判定。

规则分两级。**【必】**：违反即构成审查发现。**【宜】**：默认遵守，每处例外都必须写出理由。参考来源见 §1.3，完整清单见 §15。

---

## 1 适用范围

### 1.1 本规范管什么

1.1【必】本规范适用于本仓库所有 Markdown 文档：根目录文件，`docs/` 下的全部文件，`release_doc/` 与 `release_doc_dev/` 下的发布说明，以及上述文件的 `*-en.md` 英文对应文件。

1.2【必】文档改动按 AGENTS.md 的流程执行：强制开发流程、审查预算与分诊、独立审查。

### 1.2 读者

1.3【必】为三类读者写作：使用应用的读者、修改应用的开发者、审查本次改动的模型会话。写成的句子要让这三类读者只读一次，只得到一种理解。

1.4【必】不写宣传文案。只起赞美作用的词不用，例如「强大」「稳定高效」「一站式」「业界领先」。

### 1.3 与三个参考来源的关系

1.5【必】采用 §15 所列三个来源的原则，不声称符合其中任何一个。本仓库不实现 ASD-STE100，也没有批准词词典。词表是 §8.4 的术语表。

1.6【必】英文规则取自 ASD-STE100。该标准 Issue 9（2025-01-15）有 9 个部分、53 条写作规则，以及约 900 个批准词的词典。§6.2、§6.4、§6.7、§7.1 至 §7.3、§12.1 至 §12.2 改编自它的规则。

1.7【必】中文句长上限（§6.5）、受限制的「的」字链（§7.15）、禁用名词化与四个中文情态词（§7.7、§7.10）取自 STC-0.1。它按中文语法重建了这些原则。

1.8【必】文件命名（§3）、中文文档的标点约定和 §2 的文档体系结构取自 ruanyf/document-style-guide。

### 1.4 本规范不管什么

1.9【必】代码注释以 AGENTS.md 的 *Editing and localization* 一节为准。注释只用英文，且只写在代码自身说不清的地方。该节对注释的效力高于本文件。

1.10【必】token 的取值以 `docs/design-style-en.md` 为准：颜色、字号、圆角、间距、动效时长。本文件管怎么写文档，不管界面长什么样。

1.11【必】子系统行为以 `docs/developer-notes-en.md` 为准。复述它而不链接它的文档，等于给同一个事实指定了两个负责人。

1.12【必】源码树以 `ARCHITECTURE.md` 为准。自己再画一份源码树的文档，会与真实的树脱节。

1.13【必】提交信息格式、审查器设置和测试分层不在本文件的规定范围内。这些都归 AGENTS.md 管，按上文的交叉引用去读。

1.14【必】发布流程写在 `docs/releasing-en.md`。不在计划文档里再写第二套发布流程。

1.15【宜】必须写到其他子系统时，写明那个事实归哪份文档维护。

1.16【宜】单份文档不超过 400 行。更长的内容独立成节或链接到负责它的文档，因为读者在第一个扫不清的屏幕上就会停下。

## 2 文档类型与位置

2.1【必】文档放在 §2.2 为其类型给出的位置。新文档必须在第一段声明它的类型。

### 2.2 类型、位置与必备章节

| 类型 | 文件 | 必备章节（按此顺序） | 状态头 |
| --- | --- | --- | --- |
| README | `README.md` 与 `README-ZH.md` | 应用是什么；功能列表，每项一个链接；安装；权限；另一语言版本的链接 | 不需要 |
| 架构图 | `ARCHITECTURE.md` | 用途；Tree（逐文件）；归属与分层规则；线程规则；每类改动该放在哪里 | 不需要，源码树本身就反映时效 |
| Agent 说明 | `AGENTS.md` | 构建、运行与验证；测试分层；流程；审查；不变量 | 不需要，它描述当下 |
| 开发笔记 | `docs/developer-notes.md` 与 `docs/developer-notes-en.md` | 每个子系统一个 `##` 节。每节写契约、实测事实和复现它的命令 | 不需要 |
| 设计风格 | `docs/design-style.md` 与 `docs/design-style-en.md` | 适用范围；原则；按维度编号的章节（颜色、文字、间距、圆角、层级、动效、语言）；已记录的偏离 | 不需要，规范文件按定义就是当下的 |
| 界面改造计划 | `docs/ui-refresh-plan.md` 与 `docs/ui-refresh-plan-en.md` | 基本规则；实测基线；各阶段；每阶段落下的断言 | 必须有：一行 `状态：`，写明当前阶段 |
| 发布流程 | `docs/releasing.md` 与 `docs/releasing-en.md` | 生产流水线；开发渠道；签名；图标生成；卸载时不清理的内容 | 不需要 |
| 计划与审计文档 | `docs/*-plan.md` 与 `docs/*-audit.md` | 第一条列表项写 `状态：` 或 `Status:`；范围；发现或各阶段；决策与理由；待定问题 | 必须有，且必须带日期 |
| 审查积压 | `docs/review-backlog.md` | 说明条目含义的段首文字；未决表格；已关闭条目；订正 | 不需要，每条自带日期 |
| 发布说明 | `release_doc/<版本>.md` | 一行 locale 标记；版本标题；新增内容；说明 | 只需要版本标题，文件名即版本 |

2.3【必】计划和审计文档、界面改造计划必须写状态头。状态头写当下为真的事实，例如 `状态：设计定稿，代码未动`、`Status: design agreed, code not started`，或者其他读者能对着仓库核对的写法。

2.4【必】状态头必须保持为真。后一次改动已使它不成立，它仍写着「已评审通过」或 `implemented`，这是一处缺陷，不是可以留到下次的细节。

2.5【必】发布说明放 `release_doc/<版本>.md`，`<版本>` 取自 `Cargo.toml`。开发构建通过 `scripts/dev-restart.sh` 读取 `release_doc_dev/<版本>.md`。

2.6【必】发布说明的每一条写成用户能在运行中的应用里核对的事实。不复述其他文档里的规则。

2.7【必】判断一条发布说明是否冻结，看它**自己的通道和版本**，不看它放在哪个文件名下。两个通道是彼此独立的 feed：
`scripts/release.sh` 把 `release_doc/<版本>.md` 发到正式 feed，`scripts/release-dev.sh` 把 `release_doc_dev/<版本>.md` 发到开发 feed。
两边可以使用同一个版本号，所以一个版本出现在其中一个 feed，**不能证明**另一个也发布了：开发通道可能已发 0.2.6，而
`release_doc/0.2.6.md` 还只是草稿；反过来同样可能。只有当**这个文件**随它自己的构建发布到它自己的 feed 之后，它才被冻结。

2.8【必】已冻结的发布说明不得修改；修改其他任何一份之前，必须先确认它具体是哪一份。冻结的说明是某个已发布版本对用户说过的话：
它在应用里展示过、被发布页引用过、也被不再更新仓库的人读过。后来发现的更正——改错的表述、补漏的条目、措辞调整——不会让旧说明变错，
只会让它成为历史，应当写进下一个版本的说明。**尚未发布的草稿可以改**，两个通道都是：修正还没发出去的说明、为正在准备的版本写说明，
本来就是发布流程的一部分。动手前先弄清是哪一个文件——哪个通道、哪个版本、该版本在该通道有没有发布过——并在提交信息里写明。

## 3 文件命名与位置

3.1【必】新建文档的文件名只用小写 ASCII 字母、数字和连字符。不用空格，不用全角字符，不用下划线。§2 已经固定下来的名字是例外：`README.md`、`README-ZH.md`、`AGENTS.md`、`ARCHITECTURE.md` 和 `release_doc/<version>.md` 保持仓库与工具要求的写法。

3.2【必】中文文档的英文对应文件加 `-en` 后缀，中文文件不加后缀。例如 `docs/developer-notes.md` 是中文文件，`docs/developer-notes-en.md` 是英文文件。这是本仓库既有文档已经在用的约定。

3.3【必】中文文档放在 `docs/` 下。根目录文件只有四类：说明文件（`AGENTS.md`）、源码图谱（`ARCHITECTURE.md`）、README 或许可证。

3.4【必】成对文件用同一个词干。`${stem}.md` 与 `${stem}-en.md` 因此天然成对，脚本只看文件名就能发现缺了哪一份。根目录文件只有词干指明时才成对（`README.md` 与 `README-ZH.md`）；发布说明是一个文件里放三个 locale 段，不是一对文件。

## 4 双语对应规则

4.1【必】两份文件在同一次提交中一起改。只改一份，另一份就在描述旧行为。

4.2【必】一份文件不引入另一份没有的说法。一句话、一个数字、一条命令或一条警告只出现在一种语言里，就是分歧，即使另一份读得通。

4.3【必】两份文件在事实问题上冲突时，以与代码和实测行为一致的那一份为准，并在同一次改动中改正另一份。唯一例外是设计风格文档：按 AGENTS.md 的 *UI design system*，该文档优先，代码是缺陷。

4.4【必】两份文件的规则编号完全相同。同一个编号在两份文件里指同一条规则。

4.5【宜】表格行、列表项和标题保持相同顺序。中文版重排章节后，双语 diff 就读不出改了什么。

4.6【必】两份文件互相链接：各自在第一段写出另一份的路径，并写明哪一份是规范版本。中文版必须写出 `docs/doc-style-en.md` 是规范版本。

4.7【必】对应文件里不翻译用户可见文案。按应用在该 locale 下渲染的原样引用，并写明 locale。

## 5 标题

5.1【必】每个文件只用一行一级标题，它就是文档标题。

5.2【必】`docs/` 内的文档最多用三级标题：`#`、`##`、`###`。只有超过 300 行的文档可以用四级标题。

5.3【必】标题层级不能跳级。一级标题下面直接出现三级标题，是缺陷。

5.4【必】不写孤立的子标题。同级标题只有一个时，这条内容写成列表项，不多占一级。

5.5【必】下级标题不重复上级标题的名字。在 `## 剪贴板历史` 下写 `### 存储`，不写 `### 剪贴板历史`。

5.6【必】标题末尾不加句号、冒号、逗号或分号。

5.7【必】同一文件内标题的大小写风格统一。英文文档全用句首大写，或全用词首大写，不混用。

5.8【宜】被按节号引用的文档给标题编号，比如设计风格文档。编号与标题是一个整体：`## 3. 颜色`。

5.9【必】标题写成名词短语或问句。不把一句话写成标题。

## 6 句子与段落

6.1【必】一句一事。一个句号内只写一个动作，或一条事实。两个动作就写两句，或写成编号列表。

6.2【必】英文操作程序中的句子不超过 20 个词。计数方法见 6.4。

6.3【必】英文说明性句子不超过 25 个词。

6.4【必】每个行内代码、每个标识符、每个带单位的数字、每段引用文字、每个代码块各算 1 个词。Markdown 链接按链接文字计数，不按 URL 计数。连字符复合词算 1 个词。

6.5【必】中文操作程序中的句子不超过 30 字，说明性句子不超过 40 字。每个汉字算 1 字，每个行内代码、数字或引用文字算 1 字，标点不计。

6.6【必】中文句子最多 2 个逗号。列举用的顿号不计。超过 2 个逗号时，拆句或改写成列表。

6.7【必】条件在前，动作在后：`如果日志窗口不可读，报告 build timestamp: unverified。`，英文写作 `If the log window is unreadable, report build timestamp: unverified.`

6.8【必】主语换了就换句。不让逗号悄悄带进一个新主语，例如 `服务器重启后，打开浏览器，显示登录页。`

6.9【必】一个段落一个主题，最多 6 句。需要第 7 句时，加小标题或改用列表。

6.10【必】结论写在段落第一句。理由和细节写在后面。

6.11【必】并列项达到 3 个时，用列表或表格，不写成长段落。

6.12【必】一个步骤写成一条编号项，只含一个动作。步骤从 1 开始编号，预期结果另起一行写在步骤之后。

## 7 语态与情态

7.1【必】用主动语态，写出动作的执行者。写「app 写出启动记录」，不写「启动记录被写出」。

7.2【宜】说明性文字只在执行者未知或不重要时用被动语态。

7.3【必】英文只用一般现在时、一般过去时或一般将来时。简单时态能说清的地方，不用复合助动词结构。

7.4【必】操作步骤用祈使句：`运行 scripts/gate.sh`，英文写 `Run scripts/gate.sh`，不写「您应该运行」。

7.5【必】英文不用缩写形式。写 `do not`、`cannot`、`it is`。

7.6【必】英文不把动作名词化。写 `delete the entry`，不写 `perform the deletion of the entry`。

7.7【必】中文不在动词前写「进行」「予以」「加以」「实施」「实现」。直接写动词：写「删除异常数据」，不写「对异常数据予以删除」。

7.8【必】英文情态词只用下表四个，每个只有一个含义：

| 情态词 | 含义 | 不写 |
| --- | --- | --- |
| must | 强制。不做就会出错 | should, need to, required to, have to |
| do not | 禁止 | must not, avoid, never（警告级除外） |
| can | 允许。读者也可以不做 | may, might, could |
| recommended | 推荐，并写出理由 | should, ideally, best practice, 最好, 尽量 |

7.9【必】规范文字里不写 `should`。人读它是可选项，模型读它也是可选项，用 `should` 写出的要求会被当成建议，不会被遵守。

7.10【必】中文情态词只有四个：「必须」（强制）、「不要」（禁止）、「可以」（允许）、「建议」（推荐，写出理由）。禁用「应」「应当」「需」「务必」「不得」「最好」「宜」。

7.11【必】不用双重否定。写「必须检查电源」，不写「不能不检查电源」。

7.12【必】能写数字、名称或完整清单的地方不用模糊词：「适当」「相关」「若干」「某些」「尽量」「及时」「基本上」和句末的「等」。写「60 个目录」，不写「若干目录」。

7.13【必】不用万能动词，例如「处理」「搞」「弄」。写出具体动作：「修复这个报错」。

7.14【必】表示强制时用「必须」，不用「应」。「应」带有与英文 `should` 相同的可选意味。

7.15【宜】一个中文名词短语最多 2 个「的」。出现第 3 个「的」说明定语叠得太深：写「用户账户安全设置的默认值」，不写「用户的账户的安全设置的默认值」。

7.16【必】不用「；」把两个句子连成一个。写成两句，或者写成一个列表。表格单元、代码和引用的命令里的「；」是数据而不是行文，不改。

## 8 术语

8.1【必】一词一义，一义一词。两种语言都如此，整份文件都如此。

8.2【必】本仓库的概念用 §8.4 表中给出的词。文档需要表中没有的词时，先把该词加进表里，两份文件同时加，写明唯一含义和禁用替代词。

8.3【必】表中列为禁用的替代词一律不用，即使普通英文可以接受。

### 8.4 术语表

| 词（英文） | 在本仓库的唯一含义 | 不写 |
| --- | --- | --- |
| 浮窗（overlay） | 切换器画在桌面上方的那块浮动面板 | 弹窗、浮层、HUD |
| 切换器（switcher） | 召唤 → 循环 → 抬升这一组界面，以及拥有它的那个功能 | 应用切换器、cmd+tab 工具、窗口列表 |
| 卡片（card） | 浮窗里一个可选的窗口，分仅图标卡片与缩略图卡片两种 | 磁贴、条目、单元 |
| 剪贴板选择器（clipboard picker） | 列出剪贴板历史条目的面板 | 剪贴板窗口、粘贴面板 |
| 剪贴板详情面板（clipboard detail panel） | 完整显示一条条目的第二个面板 | 预览窗口、详情视图 |
| 设置窗口（settings window） | 带侧边栏及其各页的那个窗口 | 偏好设置、选项对话框 |
| 引导（onboarding guide） | 首次运行时申请权限与快捷键的窗口 | 欢迎向导、教程 |
| 开发构建（dev bundle） | `dist/Oh-My-Tab-Dev.app`，已签名的开发版 | debug 版、测试版 app |
| launchd 任务（launchd job） | 为 app 或其 Finder 扩展注册到 launchd 的任务 | 守护进程、服务、agent |
| worktree | 本仓库的一个 git worktree。同一时刻全仓库只跑一次构建/测试/启动事务 | 检出、副本、克隆 |
| 门禁（gate） | `scripts/gate.sh` 及其各层。每一层打印一行 PASSED、FAILED 或 NOT RUN | CI 运行、测试套件、检查 |
| A1 层（tier A1） | 由脚本判定通过与否的 headless 测试与 GUI 冒烟运行器 | 冒烟层、单元测试 |
| A2 层（tier A2） | 由脚本判定通过与否的 e2e 场景，位于 `scripts/e2e/` | 集成测试、UI 测试 |
| B 层（tier B） | 由人或 Agent 判定的部分：手感、首轮界面审查、失败分诊、缺陷调查。它会判定，但不作为门禁证据，因此 B 层发现必须落成 A 层断言 | 手工测试 |
| 冒烟运行器（smoke runner） | A1 层运行、按 `smoke-result:` 行分类的一个 `#[ignore]` 测试 | 冒烟测试、GUI 测试 |
| e2e 场景（e2e scenario） | 经 `scripts/e2e/run-all.sh` 运行的一个 `scripts/e2e/*.sh` 脚本 | e2e 测试、A2 测试 |
| 干扰闸门（disturbance switch） | 「抢焦点」「覆盖屏幕」「改动系统偏好」三类干扰各自的授权开关：`--include-focus`、`--include-screen`、`--include-prefs` | 选项、开关 |
| 审查会话（reviewer session） | 属于某个任务的唯一一个 `scripts/agent-review.sh` 会话 | 审查机器人、ChatGPT 会话 |
| 审查轮次（review round） | 审查器的一整轮，以给出结论为止 | 审查、迭代、一次通过 |
| 审查积压（review backlog） | `docs/review-backlog.md`，以及其中记录的延后发现 | 待办列表、已知问题 |
| 辅助功能权限（Accessibility permission） | 事件 tap 与 AX 操作所需的 TCC 授权 | AX 权限、特殊权限 |
| 屏幕录制权限（Screen Recording permission） | 缩略图截图所需的 TCC 授权。没有它，app 回退到图标 | 截图权限、屏幕访问 |
| 用户可见文案（user-visible wording） | app 画出来的文字，存放在 `t()`、`tf()`、`t_count()` 中 | 界面文字、标签、字符串 |

## 9 代码、数据与界面字符串

9.1【必】路径、命令、配置键、标识符、selector、文件名和状态名用行内代码：`~/.config/oh-my-tab/config.toml`、`scripts/gate.sh`、`needs_in_place_control_sync`、`SectionHeader`。

9.2【必】命令输出放在代码块里，生成它的命令紧挨在代码块之前。没有命令的代码块是无法核对的引用。

9.3【必】用户可见文案按 app 渲染的原样引用。不改写，不译出它所属的 locale，不改大小写。各 locale 写法不同时，写明 locale。

9.4【必】面向用户的文档不出现原始翻译 key、app 不显示的配置键、枚举名、十六进制值、VID、PID 或内部预设 id。这些写进开发者文档，用行内代码，紧挨显示真实文案的界面。

9.5【必】开发者日志一律用英文，中文文档里也是如此。日志行原样引用，并写明它来自哪个日志文件。

9.6【必】一组实测值写成表格。生成每一列的命令写在表题或表格上一句里。

## 10 数字、单位、日期与时间

10.1【必】每个定量说法都必须能用一条点名的命令复现。该命令写在数字所在的同一节。

10.2【必】测量仪器变了，数字立即作废。引用它的每一处文档在同一次改动中一起改。这是 AGENTS.md *What the reviewer is asked to weigh here* 一节对审查员的要求。

10.3【必】数量用阿拉伯数字并带单位。不写成汉字数字。

10.4【必】数字与单位之间加一个空格（9.1 GB、750 ms、60 pt），`%` 和 `°` 前不加（80%、15°）。

10.5【必】表示范围时两端都写单位：`10 V 至 20 V`、`60 pt 至 76 pt`，英文写作 `10 V to 20 V`。不只在末尾写一次单位。

10.6【必】日期用 ISO 8601：2026-10-24。

10.7【必】文档涉及不止一个时区时必须写时区，例如 `2026-10-24 09:30（Asia/Shanghai）`。

10.8【必】增减写「增加到」「增加了」「降低到」「降低了」，或英文 `increased to`、`increased by`、`decreased to`、`decreased by`。不写「减少 3 倍」或 `reduced by 3 times`。

## 11 表格、列表、链接、交叉引用与图

11.1【必】3 个以上并列项且带相同属性时用表格。3 个以上不带属性的并列项用列表。

11.2【必】仓库内的文件按仓库相对路径引用，用行内代码，可以带行号：`docs/developer-notes-en.md:596`。不用隐藏路径的相对链接。

11.3【必】不写「如上」「同上」「前文所述」「see above」「as stated earlier」。写出节号和路径。

11.4【必】链接文字说明目标是什么。写 `[门禁脚本](scripts/gate.sh)`，不写 `[这里]`。

11.5【必】外部链接写明是哪个页面。不链接搜索结果页，不链接重定向。

11.6【必】有分支的流程用 Mermaid 代码块或 ASCII 代码块画出来。读者要同时记住 3 个结果时，不用散文描述分支。

11.7【必】表格不超过 7 列。更宽的表格拆成两张表或一个列表。

## 12 警告与破坏性操作

12.1【必】两级对应关系如下：

| 级别 | 用于 | 标记 |
| --- | --- | --- |
| 警告 / WARNING | 可能造成人员受伤，或泄露隐私数据 | `警告：` / `WARNING:` |
| 注意 / CAUTION | 可能造成数据丢失、安装损坏或应用不可用 | `注意：` / `CAUTION:` |

12.2【必】第一句写指令，第二句写具体后果。例如：`注意：先删除历史文件，再删除钥匙串项。顺序反了，磁盘上会留下永远无法解密的密文。`

12.3【必】警告放在它适用的步骤之前，写在步骤之外，不放在步骤之后。

12.4【必】一条警告只讲一个风险。有两个风险就写两条。

12.5【必】破坏性命令必须写明它毁掉什么、怎样恢复：`git reset`、`rm`、强推、`scripts/agent-review.sh --finish`、删除钥匙串项。恢复的办法写不出来的，必须写明「无法恢复」。

12.6【必】警告不放进表格单元格。警告需要独立成段。

## 13 审查与维护

13.1【必】文档改动与代码改动走同一套独立审查，适用 AGENTS.md 中相同的预算与分诊规则。

13.2【必】过期的文档属于缺陷类。文档描述的行为 app 已不具备，即使严重度标为低，也在本轮范围内。

13.3【必】代码是事实时，改正文档。设计风格文档是唯一例外：AGENTS.md 规定该文档优先，代码是缺陷。

13.4【必】延后处理的文档发现记入 `docs/review-backlog.md`，写明轮次、严重度、延后理由和把它带回来的触发条件。

13.5【必】条目对应的工作落地后删掉该条，并在提交信息或发布说明里讲明。

13.6【必】文档与它所描述的代码在同一次改动中一起更新。事后再用一个提交补文档，就是 §13.2 所说的缺陷。

13.7【必】发版前重读 §2.4：逐个核对状态头与源码树，不再成立的状态头在本次发版中改正。

13.8【宜】在本文件里新增一条编号规则，而不是新增一段指引。审查员可以引用规则编号，没法引用一段气氛。

发布前逐条核对。每一条后面是它检查的规则编号。

- [ ] 已在其所属通道发布过的发布说明一条都没改；改动的草稿都是该通道尚未发布的版本（§2.7、§2.8）。
- [ ] 计划、审计、改造计划类文档有状态头，且当下为真（§2.3、§2.4）。
- [ ] 文件名是小写 ASCII 且无空格，成对文件词干一致（§3.1、§3.4）。
- [ ] 两份文件在同一次提交中一起改了，规则编号相同（§4.1、§4.4）。
- [ ] 两份文件互相链接，并写明哪一份是规范版本（§4.6）。
- [ ] 没有跳级、孤立或重复上级名称的标题（§5.3、§5.4、§5.5）。
- [ ] 英文句子按 §6.4 计数，步骤句不超过 20 词，说明句不超过 25 词（§6.2、§6.3）。
- [ ] 没有用「；」把两句行文连成一句；表格单元与引用的命令保持原样（§7.16）。
- [ ] 中文句子不超过 30 字或 40 字，每句最多 2 个逗号（§6.5、§6.6）。

- [ ] 用户可见文案原样引用，没有原始翻译 key（§9.3、§9.4）。
- [ ] 每个数字都有点名的那条复现命令（§10.1）。
- [ ] 数字与单位间有空格，范围两端带单位，日期是 ISO 8601（§10.4、§10.5、§10.6）。
- [ ] 没有「如上」「同上」，没有裸「这里」链接，文件链接都带路径（§11.2、§11.3、§11.4）。

- [ ] 每条破坏性命令写明了毁掉什么、怎样恢复（§12.5）。
